# Vault Ontology

Shared definitions for how the owner and AI agents use the vault: the note types, how a capture is classified, and how notes are named. Every agent reads it before filing anything and proposes edits here when a correction shows a rule is missing or wrong. Agent operating rules are in `AGENTS.md`.

## 1. Hierarchy

```
Mission → Responsibility → Project → Epic → Story → Task
                                               ↑       ↑
                                            Issue (affects a Story or Task)
Sprint ← Story            Event / Meeting → related to anything
Reference, Note, People, Organizations, Sessions, Plans: supporting notes
```

**Every work item has a parent.** A Task's parent is always a Story, never an Epic. If no fitting parent exists, the agent proposes creating one or asks. Nothing is left dangling.

## 2. Definitions

| Type | What it is | Key properties |
|---|---|---|
| **Mission** | One of the permanent institutional missions of the academic role: Teaching, Research, Third Mission, Mentoring. Fixed set. | — |
| **Responsibility** | An ongoing area of accountability serving ≥1 Mission (e.g. PhD Supervision, Funding Acquisition). Never "done". | `missions` |
| **Project** | A bounded endeavour with its own identity (a grant, a course, a PhD student, a thesis, a school) serving ≥1 Responsibility. | `org`, `activities`, `status: Proposal / Under Review / Funded / Ongoing / Closed` (Under Review = submitted, awaiting an outcome; Funded = grant awarded and running), `priority`, `tags`, `archive` |
| **Epic** | The **largest container of work inside a Project**. It groups Stories toward a bigger goal. Its kind (milestone, work package, yearly cycle) depends on the owner's role in that project. Reached **top-down** (splitting a project) or **bottom-up** (a piece of work turns out to need several distinct results). | `projects`, `archive`; status and priority derived |
| **Story** | A **complete, concrete result**, usable on its own: a paper written, lessons prepared, a proposal submitted. Any size. | `epics`, `sprints`, `archive`; status and priority derived from its Tasks |
| **Task** | A **concrete but partial** contribution to a Story: a section, a revision, an analysis. It produces something real, but doesn't complete the result by itself. May serve several Stories. | `stories`, `assignees`, `status: Backlog / Planning / In Progress / Done`, `priority: Urgent / High / Medium / Low` (default Medium), `scheduled` |
| **Issue** | A problem, bug or limitation affecting existing work, attached **only to the Task or Story it affects**. **Blocking** (`blocking: true`): prevents progress and is addressed now via Tasks. **Non-blocking**: a known limitation to consider in the future. | `affects`, `blocking`, `status: Open / Resolved` |
| **Sprint** | A time box of about 2 weeks. The current sprint is the one where today falls between `start` and `end`. | `start`, `end` |
| **Event** | Anything dated: a meeting, lesson, conference, deadline or talk. One EVT note per occurrence. | `start`, `end` or `duration`, `people`, `related to`, `calendar_ids` (the calendar event keys) |
| **Meeting** | An Event with minutes and action items: `type: [Events, Meetings]`. Action items are candidates for new Tasks. | as Event |
| **Reference** | External knowledge that is consulted, not executed: a paper, call, dataset, tool or link. Subtypes via an extra `type` (e.g. `[[Grants]]`). A **paper** also has `type: [[Papers]]`. | `url`; papers: `authors` (first author + "et al."), `year`, `venue`, `doi`, `arxiv`, `zotero` |
| **Note** | Own thinking that isn't work yet: ideas, drafts, open questions. It becomes an Epic/Story/Task only when it gets planned. | — |
| **Session** | One conversation between the owner and an agent (one CLI session id, however many days it spans): goal, decisions, notes touched, corrections, open points. | `start`, `end`, `agent` (the harness: `[[CLAUDE\|Claude Code]]` or `[[CODEX\|Codex]]`), `model`, `session_id`, `transcript`, `plans`, `topics`, `touched` |
| **Session Transcript** | The readable record of one agent session, generated by `export_transcript.py`, never written by hand. | `session`, `agent`, `model`, `session_id`, `start`, `end`, `privacy_check: clear / flagged / not run / pending`, `privacy_flags` |
| **Plan** | A plan an agent wrote before acting, kept for the record. Filename comes from the agent's tool, so it is not an ID. | `session`, `status: Draft / Approved / Done / Dropped` |
| **People / Organizations** | Entities. People link to organizations with `org`. | see templates |
| **Daily Note** | Journal page named by date (`YYYY-MM-DD`). | — |

## 3. How an agent classifies a capture

Questions asked in order. The first "yes" wins.

1. **Does it have a date/time at which something happens?** (a meeting, deadline, lesson, conference) → **Event** (Meeting if it has people and minutes). If it *also* implies work, propose the work item too.
2. **Is it something going wrong, or a limitation?** → **Issue**, attached to the Task or Story it affects. Blocking if it stops current work, non-blocking otherwise.
3. **Is it external material to consult?** → **Reference**.
4. **Is it an idea or question not yet planned?** → **Note** (or, if you say so, a Backlog work item).
5. **Is it work?** Then pick the level:
   - Finishing it needs **several distinct complete results** → **Epic**.
   - It **is** one complete, usable result → **Story**.
   - It is a **partial step** toward a result → **Task**.
6. **Is it a new bounded endeavour with its own identity** (funding, course, student)? → **Project**.

Then the agent finds the parent among the active notes, sets the language, proposes the Tasks for a Story, and gets nimble's second opinion. The procedure is the `capture` skill.

## 4. Naming, IDs and links

- **Filename = unique ID** `<PREFIX>-<NNNN>`, one counter per type (next = highest existing + 1).
- In Obsidian, create the note in its type folder and type the title. Templater (`Templates/Scripts/new_entity.js`) puts the title in `name`/`aliases` and renames the file to the next ID. Notes that already have a `name` are left untouched.
- The displayed name lives in `name`, copied into `aliases` so link autocomplete finds it. Names may repeat and should be short. The project context comes from the links, not from the name.
- `title` is **not** the display name: on People it holds the honorific (`1 - Prof.`, `2 - Ing.`).
- Links are written `[[TSK-0042|Title]]`, so they stay readable in raw Markdown.
- If a note changes type, its prefix changes: the file is renamed and every link to it is rewritten.

| Type | Prefix | Type | Prefix |
|---|---|---|---|
| Missions | `MIS` | Issues | `ISS` |
| Responsibilities | `RES` | Sprints | `SPR` |
| Projects | `PRJ` | Events / Meetings | `EVT` |
| Epics | `EPC` | References | `REF` |
| Stories | `STR` | People | `PER` |
| Tasks | `TSK` | Organizations | `ORG` |
| Notes | `NOT` | Sessions | `SES` |

Not renamed: Daily Notes (date filenames), Plans (tool-generated filenames), Session Transcripts (`<date>-<agent>-<session id8>`), Categories, Bases, Templates, root index notes.

Templater ignores new files in `99 - Agents/` and `00 - Data/Plans/`. Anywhere else it executes any `<% … %>` text in a newly created note, so agents must never write it there.

## 5. General rules

- **Language**: match the project (*Machine Learning per la Salute* → Italian). For a new project, use the language of the capture.
- **Autonomy**: the agent proposes, the owner approves, then the agent writes. Every capture proposal and its outcome is logged.
- **Status and priority**: Tasks carry `status` and `priority`; Projects carry `priority`. A Story's or Epic's status and priority are **only derived** by base formulas (priority = the highest among its open Tasks, or among all if every one is Done). Never write them.
- **Sprints**: Stories are planned into sprints. Tasks inherit the sprint from their Story and have no `sprints` of their own.
- **Archive**: `archive: true` hides finished items from the Active views. Nothing is ever deleted.
- **Privacy**: any note may carry `privacy: [<category>, …]` (now `clinical`, `personal`).

## 6. Worked examples

All drawn from the example lab in this vault.

| Capture | Type | Parent | Why |
| --- | --- | --- | --- |
| "Write the methods section of Marco's review" | Task | Story *Systematic review submitted* | A partial step: the Story's result is the whole submitted review. |
| "Prepare the module 1 lessons" | Story | Epic *Edizione 26-27* | One complete result (the set of lessons); the individual lessons are Tasks. |
| "Build the multimodal model for CARDIO-FM" | Epic | Project *CARDIO-FM* | Needs several results (baselines, fusion prototype, evaluation, …). |
| "MRI slice thickness differs between the two scanners" | Issue, blocking | Task *Resample MRI to a common slice thickness* | It stops the current approach, so it is attached to the Task it affects. |
| "Conformal prediction could give calibrated sets for the fusion model" | Note (or a Backlog Task, if you plan it) | related to Epic *Multimodal model* | An idea, not yet planned work. |
| "CARDIO-FM kick-off 06/10 10:00" | Event + Meeting | related to Project *CARDIO-FM* | Dated, with people and minutes. |
